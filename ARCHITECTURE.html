What this system actually is

Chief of Staff is an ingestion and retrieval pipeline with a chat surface on top — not a chat application with tools attached. That distinction drives every design decision below: the expensive, error-prone work happens asynchronously against raw source data, and by the time a user asks a question the hard problems are already solved and stored.

There are four distinct subsystems, and they fail independently:

SubsystemRuns onTriggerIf it stops
Ingestion — get raw email/calendar inVercel (webhook) + local scripts (backfill)Gmail push via Pub/Sub; manual backfillNew email stops arriving. Silent — this went unnoticed for three months.
Processing — turn raw into structuredRailway worker (BullMQ)Queue jobsEmail arrives but has no summary, category, or embedding. Visible as blank rows.
Retrieval — answer questionsVercel (/api/ask)User queryAsk AI fails loudly. The only subsystem whose failure is obvious.
Reconciliation — repair the aboveRailway worker (cron)Every 6 hoursTransient failures become permanent data loss.
Why the split matters. Three of the four subsystems fail silently. A user cannot distinguish "no financial emails this week" from "financial extraction has been broken since Tuesday". Reconciliation exists because the other three will fail, and the cost of a missed failure is wrong answers delivered confidently.

Data path, end to end

Gmail → Pub/Sub topic → push subscription → /api/webhooks/gmail → raw_events + queue job → worker fetches full message → contacts + communications → triage → conditional financial extraction → transactions_raw → dedup → transactions_normalized → embeddings → memory_chunks → operational state recompute → surfaced in Inbox, Finance, Commitments, Daily Brief, and Ask AI.

Every arrow is a place where work can be lost. The ones that proved fragile in practice are marked in the flow pages that follow.

Flow 1 · Inbound

How email gets in

Two paths write to communications, and they are not equivalent. Understanding which one is running explains most operational surprises.

A

Live path — Gmail push near real-time

A registered Gmail watch publishes mailbox changes to a Pub/Sub topic; a push subscription forwards them to /api/webhooks/gmail. The route resolves the account, walks Gmail history since the stored cursor, filters to messages with INBOX and without SENT, writes raw_events, and enqueues one job per message.

Four independent things must all hold: the watch must be current (it expires after 7 days and is renewed 4×/day); the topic must live in the same Google Cloud project as the OAuth client that minted the token; that topic must grant publish rights to gmail-api-push@system.gserviceaccount.com; and a push subscription must point at the live webhook URL. Any one missing produces total silence with no error anywhere — three of the four were wrong simultaneously in production.

Because the message is self-sent mail is excluded by design, a self-addressed test email will never produce a raw_event. Testing this path requires genuinely external mail.

B

Bulk path — backfill script historical

Lists messages over a day window, skips anything already stored by external_id, writes communications directly, and enqueues a summarize job. It bypasses raw_events entirely — so the two paths have different failure signatures, and reconciliation has to cover both.

Fetches run six at a time: Gmail round-trips dominate at roughly one second each, making a serial pass over a few thousand messages take the better part of an hour.

Trade-off: write-then-enqueue. Both paths commit the database row before enqueueing its job, which means a Redis failure leaves a committed row with no pending work and nothing recording that fact — communications has no status column. The alternative, enqueue-then-write, trades silent data loss for jobs referencing rows that do not exist yet. We kept write-first and added the reconcile pass, because a delayed row is recoverable and a lost one is not.

What deliberately does not use a model

Merchant normalisation (a ~100-entry alias dictionary), sender classification, the finance gate, transaction grouping, retrieval planning, ranking, and all operational-insight generation are pure functions. They are deterministic, free, instant, and unit-testable — and they are where a model would introduce non-determinism for no benefit. When the deterministic normaliser and the model disagree on a merchant, the deterministic answer wins.

Trade-off: gating over capability. The cheapest way to improve an LLM pipeline's cost profile is usually to stop calling it, not to change models. Skipping commitment extraction for newsletters and promotions cut more cost than any model swap, and cost nothing in quality, because those categories do not contain commitments.

Flow 3 · Retrieval

How a question becomes an answer

The design premise: pure vector RAG over an inbox conflates "how much did I spend on Uber?" with a calendar invite mentioning Uber. Structured questions deserve structured retrieval, so intent routing happens before any search.

1

Classify

Regex pre-pass scores candidate intents; a gpt-4o-mini call refines intent, entities, temporal anchor, and a two-dimensional retrieval weight. Deterministic overrides then hard-set weights for query shapes we know the model gets wrong.

2

Resolve

Entity strings become IDs: people → contact rows via fuzzy match, merchants → canonical names, temporal anchors → absolute date ranges — including event-relative anchors such as "since my last salary credit", resolved by querying for that event first.

3

Plan & execute

A pure function emits a list of retrieval steps with priorities and cost estimates, trimmed to a latency budget, then run in parallel under Promise.allSettled so one slow source cannot block an answer.

4

Rank & synthesise

Heterogeneous results are normalised to a common shape and scored by a profile-aware weighted ranker (keyword, semantic, entity overlap, recency, source confidence, urgency), with per-source diversity caps so no single source floods the context. The top items become a provenance-tagged evidence block for gpt-4o.

Trade-off: fail open, not narrow. Degraded classification now widens retrieval rather than restricting it. The earlier fallback chose a single intent with zero investigative weight, which meant a slow model call silently excluded the very tables holding the answer. When a system is uncertain, searching too much costs latency; searching too little costs correctness invisibly.

Known limitation. Vector results are scored by true pgvector similarity, but the "semantic" component for SQL-sourced rows is still a keyword proxy. Ranking across sources is therefore not strictly comparable, and this is the most likely place for retrieval quality to be lost today.

Decisions · Page 5 of 5

Trade-offs taken, and what they cost

DecisionChosen becauseAccepted cost
Exact KNN, no HNSW indexAt ~2 000 emails exact search is milliseconds. An HNSW index over 1 024-dim vectors costs an estimated 50–100 MB of a 500 MB budget and must stay memory-resident; its maintenance on bulk embedding writes is what exhausted a database's disk.Search cost grows linearly. Revisit past roughly 50 000 rows — the definitions are in the schema, commented out.
Do not store rendered HTMLAt ~26 KB average it was the largest thing in the database — ~160 MB across a mailbox, against a 500 MB ceiling, and the single largest contributor to running out of disk.Opening an email costs a Gmail round-trip. Gmail is the canonical copy, so nothing is lost but latency.
60-second queue pollUpstash does not support blocking commands well, so BullMQ polls. The 5-second default consumed a 500 k/month quota in three days on idle polling alone; one hour made push-delivered email arrive an hour late, defeating the point of push.Roughly $0.40/month in polling, and up to a minute of pickup latency.
Reconcile rather than transactDatabase writes and queue enqueues cannot share a transaction across Supabase and Redis. A periodic sweep that re-enqueues anything missing a summary or embedding is simple and covers every ingestion path.Up to six hours before a dropped job is retried.
Skip, not replace, on reprocessingCommitments and tasks accumulate user state — completions, snoozes, edits. Re-deriving them would silently discard that.An email reprocessed after a parser fix keeps commitments derived from the worse input.
Clamp extracted dates to email arrivalExtraction confuses delivery dates, due dates, and DD-MM-YY ordering. A transactional alert arrives within hours of the event, making arrival time a reliable anchor.A genuinely old transaction referenced in a new email is dated wrongly. Bounded at 90 days to make that rare.
Free-tier Postgres, local pg_dumpSingle-user product; managed backups are a paid tier.Backups live on one laptop, and the ceiling is a real operational constraint rather than a theoretical one.

The through-line. Almost every defect documented here shares one shape: an error was caught, handled, and discarded, so the pipeline reported success while producing wrong or missing data. The durable fixes were not smarter prompts or bigger models — they were a unique index, a reconcile pass, checked error returns, and clamps on values a model is known to get wrong.
